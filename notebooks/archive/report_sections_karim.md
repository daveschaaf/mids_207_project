## Data Description

Our dataset comes from the H&M Personalized Fashion Recommendations competition on Kaggle, containing one year of retail transaction data (January–December 2019) across three tables. The articles table (105,542 rows, 25 columns) catalogs H&M's product inventory with attributes including product type, department, color, and garment group. The customers table (1,048,575 rows, 6 columns) contains demographic and engagement data such as age, club membership status, and fashion news subscription frequency. The transactions table (1,048,576 rows, 5 columns) records individual purchases linking customers to articles with timestamps, prices (normalized to a 0–1 scale), and sales channel identifiers.

After preprocessing, the transactions table was reduced to 1,040,101 rows through removal of 8,474 duplicate records and rows with invalid dates or out-of-range prices. The articles and customers tables retained their original row counts after cleaning. Notably, only 51,279 of 105,542 articles (48.6%) and 458,235 of 1,048,575 customers (43.7%) appear in the transaction data — the remaining records are orphaned with no purchase history.

The input to our predictive model consists of 36 engineered features spanning customer behavior (6 RFM features: days since last purchase, purchase count, total spent, average transaction value, price standard deviation, average days between purchases), customer preferences (category diversity plus 21 one-hot encoded garment group indicators), and product characteristics (4 price features and 4 popularity features). The target variable is a binary label indicating whether a customer purchased a specific product during the prediction window. Data is split chronologically to prevent temporal leakage: training uses features computed as of September 30, 2019 with October purchases as labels (83,100 pairs), validation uses features as of October 31 with November labels (90,432 pairs), and testing uses features as of November 30 with December labels (85,764 pairs). Each split maintains a 5:1 ratio of negative (non-purchased) to positive (purchased) pairs, resulting in an approximately 83.3%/16.7% class distribution.

## Data Challenges

**Class imbalance.** With a 5:1 negative sampling ratio, 83.3% of examples in each split are non-purchases. A majority classifier achieves 83.3% accuracy without learning anything from the data. We addressed this by using binary cross-entropy loss, which penalizes confident incorrect predictions, and by tracking precision, recall, and F1-score alongside accuracy to ensure the model learns to identify actual purchases rather than defaulting to the majority class.

**Heavily skewed feature distributions.** Continuous features such as total spend, number of purchases, and product prices exhibited strong right skew, with most values concentrated near zero and long tails. We applied log transformation (log1p) to seven features (avg_price, max_price, total_spent, min_price, num_purchases, sales_last_7_days, sales_last_30_days), which improved test accuracy from approximately 90% to 94% by reducing the influence of extreme outliers and creating more normally distributed inputs for the neural network.

**Temporal data leakage.** Since our model predicts future purchases, using any information from the prediction period during feature computation would inflate performance. We enforced strict as-of-date cutoffs — customer and product features are computed using only transactions occurring before each split's boundary date, ensuring the model never sees future information during training or evaluation.

**Missing and sentinel values.** The raw data contained missing values across all three tables and sentinel values (-1) in several article attribute columns. For the cleaning stage, we applied context-appropriate imputation: categorical fields were filled with "Unknown," binary indicators (FN, Active) defaulted to 0, and fashion news frequency defaulted to "NONE." For feature engineering, missing values were filled based on directional intent — recency features for inactive customers were set to above-maximum values (e.g., avg_days_between_purchases = 999) to signal minimal engagement, paired with a binary inactivity indicator so the model can distinguish imputed from real values. Price features defaulted to the global average to avoid introducing bias.

**Sparse customer and product coverage.** Over half of articles and customers in the dataset had no transaction history, meaning our feature engineering could not compute meaningful behavioral metrics for them. We addressed this by focusing the model on the 458,235 active customers and 51,279 transacted products, and by designing features that degrade gracefully for low-activity entities (e.g., single-purchase customers receive the 999-day sentinel and inactivity flag rather than undefined values).
